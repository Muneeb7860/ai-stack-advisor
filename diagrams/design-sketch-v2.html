The six decisions that shape everything downstream — start here, then go to Stack, Cost, or Trade-offs for the full picture and the reasoning behind each pick.

Cloud provider

High
AWS
PCI-DSS + SOC2 tooling maturity and fraud/ML service breadth (SageMaker, Fraud Detector) outweigh multi-cloud flexibility at this stage.

Architecture style

High
Microservices, hexagonal per service
Compliance boundary (PCI scope) benefits from service isolation; hexagonal keeps each service's domain logic testable independent of infra.

Primary database

High
PostgreSQL
Transactional integrity for financial records is non-negotiable — ACID guarantees over eventual consistency here.

LLM orchestration

Medium
Claude Sonnet + rule-based fraud model
LLM handles the support chatbot; fraud scoring itself should stay a dedicated, auditable ML model — not an LLM call, for regulatory explainability.

Compliance posture

High
SOC2 Type II + PCI-DSS Level dependent on volume
Both explicitly stated — scope PCI to the card-data path only, keep the rest of the system out of PCI scope where possible.

Team-size fit

Medium
Managed services over self-hosted
6 engineers can't also run Kafka/K8s ops — lean on RDS, managed Kubernetes, and managed queues to keep the ops surface small.

Messaging — Kafka vs. managed queue (SQS/SNS)
✓ Recommended
Kafka
You need a durable, replayable log — required for audit trails, fraud/analytics pipelines, and multiple independent consumer groups reading the same stream at different speeds.
vs
Alternative
Managed queue (SQS/SNS)
Simpler ops, no cluster to run — but no replay or durable audit history, and no fan-out to independent consumer groups.
Switch when: traffic is moderate and you don't actually need replay/audit history — Kafka's operational cost only pays off once you're using its durability guarantees.
Fraud scoring — dedicated ML model vs. LLM-based scoring
✓ Recommended
Dedicated ML model (gradient-boosted / feature store)
Regulatory explainability requires a deterministic, auditable decision path — a feature-store-backed classifier gives you that. An LLM call is neither reliably deterministic nor easily explainable to an auditor.
vs
Alternative
LLM-based scoring
Faster to prototype, no feature pipeline to build — but non-deterministic output and weak explainability make it a poor fit for a PCI-scoped decision.
Switch when: never, for the core scoring decision itself — an LLM can sit downstream to summarize why a transaction was flagged, in plain language, without being the thing that made the call.
